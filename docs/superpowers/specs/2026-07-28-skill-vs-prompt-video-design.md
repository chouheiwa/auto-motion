# “Skill 不就是 Prompt 吗？”竖屏 MG 视频设计

## 目标

把 `文章.md` 重构为一条适合抖音发布的 2–3 分钟竖屏 MG 视频。成片以真实 MiniMax TTS 为时间基准，使用 HyperFrames 镜头渲染流程，最终交付 `final.mp4`、字幕、声音素材、质量检查和完整制作证据。

## 已确认的创作方向

- 发布平台：抖音。
- 画幅：1080×1440 竖屏。
- 帧率：30fps。
- 目标时长：约 160 秒，允许在 2–3 分钟内根据正式语音和展示节奏调整。
- 叙事方案：“四层质变”。
- 视觉方向：“清晰系统蓝图”，以雾白、工程蓝、圆、连线和层级图形为主要视觉语言。
- 封面标题严格为两行：

  ```text
  Skill 不就是
  Prompt 吗？
  ```

- 第 0 帧必须是完整封面，建议稳定 18 帧后再开始转场。
- 配音方向：中文男声，冷静但有锋芒，偏技术评论而非广告腔。
- 声音方向：低密度、克制的未来感电子氛围；音效只服务关键节点。

## 内容设计

终稿控制在约 750–850 个汉字，预计结构如下：

1. 0:00–0:15：提出冲突——Skill 看起来就是 Markdown，凭什么不只是 prompt？
2. 0:15–1:45：四层质变——按需加载、脚本确定性、与 MCP/RAG 等概念的边界、方法论变成可执行约束。
3. 1:45–2:20：证据与现实价值——跨工具采用、版本化、组合和移植能力。
4. 2:20–2:35：风险——发现机制、安全与过度包装。
5. 2:35–2:40：结论——质变不在原料，而在抽象。

整理时保留原文事实、观点、因果和结论，不增加未经证实的信息。链接、日期和数字只有在真正支撑主线时才进入口播。专有名词和不可拆分短语至少包括：

- Skill / Agent Skills
- Prompt
- SKILL.md
- Claude Code
- MCP
- RAG
- Git
- API
- VS Code
- GitHub Copilot
- OpenAI Codex CLI

先生成 `production/script-final.md` 和 `production/script-change-log.md`。稿件确认前不得生成整条正式配音。

## 配音和真实时间轴

MiniMax 凭据只从项目根目录 `.env` 读取。日志仅记录变量是否存在，不输出值、认证头或包含密钥的 URL。

在音色未确定时，使用同一段 10–20 秒代表性文案生成 2–3 个试听版本。用户确认音色、语速和情绪后，优先按完整语义段落生成正式 TTS。保留去敏请求参数、响应、原始音频、服务时间戳和生成报告。

正式 SRT 只依据最终音频和服务返回的真实时间戳重建。字幕按可读语义单元切分，保留呼吸和展示空白。最终节目先冻结总帧数，再以 `总帧数 ÷ 30` 得到时长；人声不足节目终点时补静音，不拉伸人声。

## 分镜和渲染

根据冻结 SRT 拆成约 10–12 个粗粒度语义镜头。具体数量服从同一主题、因果关系和视觉概念，不按固定字幕条数机械划分。

每个镜头：

- 覆盖连续帧区间。
- 与前后镜头首尾相接。
- 从 `exampleFolder` 复制 `.claude/` 和 `run-scene.sh`。
- 把完整 `transcription-production.srt` 复制为镜头目录内的 `transcription.srt`。
- 明确填写 `SCENE_ID`、`SCENE_DURATION_SECONDS`、`OUTPUT_FILE`、`FULL_TRANSCRIPT_PATH` 和 `SCENE_TEXT`。
- 只调整上述变量和 `PROMPT` 中的创意描述，不改变非交互运行、日志过滤、输出和错误处理契约。
- 输出 1080×1440、30fps、H.264、`yuv420p`、静音且无音轨的 MP4。

统一提示词只约束语义重点和“清晰系统蓝图”艺术方向，不替渲染工具设计镜头内部 MG 动效。

严格按镜头编号单线程执行 `run-scene.sh`。每次调用保留流日志、错误日志和用户消息日志。失败重试使用新的 attempt 目录，不覆盖失败证据。

日志只能向外放行以 `[[USER_MESSAGE]]` 开头的消息，并保留：

- `render-<scene>.stream.jsonl`
- `render-<scene>.stderr.log`
- `render-<scene>.user.log`

每次渲染至少出现以下四类阶段消息，文字保持执行脚本约定：

- 需求理解和素材检查已完成。
- 开始联网搜索。
- 代码已完成，开始渲染。
- 视频已渲染完成并带输出文件名。

## 视觉设计与验收

视觉系统使用雾白背景、工程蓝主色、深蓝正文、低饱和辅助灰。主要构成元素是圆、虚线圆环、节点、连线、模块卡片和清晰的层级关系。避免高饱和赛博朋克和持续强刺激。

封面使用已确认的两行标题。第 0 帧必须完整、清晰、无黑帧、无淡入中间态，标题处于抖音安全区。检查第 0 帧、转场开始帧和转场中代表帧。建议封面稳定 18 帧；如渲染验证发现可读性不足，只增加稳定帧或重渲染相关镜头，不改动冻结配音。

逐镜头使用 FFprobe 验证分辨率、帧率、编码、像素格式、色彩信息、帧数、时长和无音轨。规格不一致时保留原始渲染并生成规范化副本。拼接后的 `production/silent-master.mp4` 总帧数必须等于冻结时间轴。

## 音乐、音效与混音

BGM 为低密度电子氛围，稳定脉冲，不使用强鼓点，不做赛博朋克风格。SFX 仅放在：

- 开场质疑。
- 四层编号出现。
- 风险段转折。
- 最终结论落点。

所有外部音频必须具备明确授权和可追溯来源。素材账本记录 URL、作者、素材 ID、授权、下载时间和 SHA-256。Cue 以整数帧定位，并换算为 48kHz 采样点。

工作格式为 48kHz 双声道。人声保持原速，BGM 在有人声时自动下压，SFX 不覆盖关键词、数字和专有名词。执行两遍响度规范化，以约 -16 LUFS 和不高于 -1 dBTP 为检查目标。

## 质量检查和审批

机器检查包括：

- 1080×1440、30fps、H.264、`yuv420p`。
- 视频总帧数与冻结时间轴一致。
- 音频为 48kHz 双声道，解码采样数到达精确节目终点。
- 音视频完整解码。
- 第 0 帧可读且非黑帧。
- 字幕、镜头和音效 cue 无越界。
- 响度和峰值符合目标。
- 输入、候选、素材、日志和检查报告的 SHA-256 绑定一致。

人工试听必须记录耳机和手机外放结果。若无法操作物理设备，两项均标为“未执行”，不得假称通过。

无法代做的物理设备试听属于“发布前人工事项”，不阻止生成技术验收通过的 `final.mp4`，但 `approval.json` 必须把机器审批状态与发布审批状态分开记录：机器审批可以通过，发布审批保持 `pending_manual_listening`。最终汇报必须醒目标出发布前仍需补做耳机和手机外放完整试听，不得宣称已可直接发布。

只有 `production/approval.json` 绑定的机器检查全部通过，且除已明确允许挂起的物理试听外不存在其他失败项，才允许在根目录原子生成 `final.mp4`。交付后再次核验哈希、规格和完整解码。

## 错误处理

- 输入哈希变化：立即停止，要求确认，不静默继续。
- TTS 断句或发音错误：修改标点、分段或发音控制，只重生成受影响段落。
- 镜头长时间无阶段消息：先检查日志、文件更新时间和渲染进程，再根据退出码判断。
- 镜头规格不符：保留原始文件，生成规范化副本。
- 视觉检查失败：只重渲染相关镜头，不重做冻结配音。
- 外部素材授权不清：不使用，改选可追溯素材或自制确定性声音。
- 机器 QC 失败：不得生成或替换根目录 `final.mp4`。

## 阶段关卡

1. 稿件审核：确认终稿、开场、预计时长、修改点和专有名词。
2. 音色试听：确认 MiniMax 音色、语速和情绪。
3. 配音审核：确认完整配音、断句和发音。
4. 时间轴冻结：确认真实 SRT、总帧数和镜头计划。
5. 视觉检查：确认封面和代表帧。
6. 声音检查：确认混音候选和无法代做的物理试听项。
7. 最终审批：检查哈希绑定后原子交付。
